# （Photo Gallery PWA）V1.4

掃 QR Code 直接開啟的喜帖式相簿。新人精選的照片放在 Google 雲端硬碟，由 Google Apps Script 提供清單；訪客也可以把自己拍的照片上傳到「另一個」共用資料夾，所有人都看得到。網站本身是純靜態檔案，放在 GitHub Pages 即可。

## V1.4 更新內容

| 項目 | 說明 |
|---|---|
| 下載方式可以選 | 多選照片後按「下載」，改成先問要「打包下載（ZIP）」還是「逐張下載」——後者不會產生壓縮檔，手機不方便解壓縮的人也能用 |
| 修正上傳失敗的問題 | 你回報的「網路或伺服器錯誤」查到很可能的原因，並修正（見下方「上傳失敗問題的排查與修正」），另外也修好一個會讓失敗原因顯示錯誤的小 bug |
| 上傳前自動壓縮 | 照片上傳前會在手機上先縮小、重新壓縮，大幅降低失敗機率、加快上傳速度（可調整或關閉） |
| 上傳逾時提示 | 上傳等待太久會顯示「逾時」而不是無限轉圈或籠統的錯誤 |

## 上傳失敗問題的排查與修正

你回報「上傳照片時顯示『網路或伺服器錯誤』」，並問是不是 Google 限制照片大小造成的。我查了 Google 官方文件與社群已知問題，這裡整理實際查到的結論：

- **Google 官方文件公開的「50MB」限制，指的是 Apps Script 主動對外發送請求（`UrlFetchApp`）的上限，不是瀏覽器上傳「進來」給 Apps Script 的限制**——這兩者是不同方向的流量，容易搞混。Google 沒有公開一個「網頁上傳進來最多幾 MB」的明確數字。
- 我也順帶確認了 V1.3 選用的技術做法（用 `text/plain` 繞過 CORS 預檢）沒有問題，這是社群公認可行的解法，不是問題來源。
- **更可能的真正原因，是手機拍的照片本身就不小**：現在的手機動輒拍出 5～15MB 的照片，轉成 Base64 文字上傳前體積還會再膨脹約三分之一（20MB 的照片變成快 27MB 的文字）。在婚禮現場常見的行動網路訊號下，一次要送出這麼大量的資料，很容易在傳輸過程中逾時或中斷——這比「被 Google 擋下來」更符合實際情況，而且沒辦法從錯誤訊息分辨到底是哪一種。
- **檢查自己的程式碼時，也真的抓到一個 bug**：伺服器如果因為「格式不符」「檔案太大」等原因拒絕，網頁全部都會顯示同一句籠統的「網路或伺服器錯誤」，等於把真正的原因蓋掉了，不管是訪客自己想排查，還是你事後想知道發生什麼事，都看不出所以然。

**這一版的修正**：
1. **上傳前自動幫照片瘦身**：選好照片後，會先在手機瀏覽器裡把長邊縮到 2400px 以內、重新壓縮成 JPEG，才送出去。已經夠小的照片不會被重新處理，避免沒必要的畫質損失。一般手機照片經過這一步，體積通常會降到原本的 1/5～1/10，上傳快很多，也大幅降低半路失敗的機率。如果縮圖這一步本身失敗（例如瀏覽器不支援解碼某些格式），會自動改用原始檔案，不會讓上傳整個卡住。
2. **錯誤訊息改成對應各自的真正原因**：檔案太大就顯示「太大」，格式不符就顯示「格式不符」，只有真的是網路或未知的伺服器問題，才會顯示「網路或伺服器錯誤」。
3. **加上明確的逾時提示**：等待超過一段時間（預設 60 秒）會顯示「上傳逾時」，不會讓人一直不知道發生什麼事。

**這些修正沒辦法在沒有真實 Apps Script 的環境完整驗證**（跟 V1.3 一樣的限制），但邏輯上會直接解決「照片太大、行動網路不穩定導致上傳失敗」這個最可能的成因。如果套用這版之後還是常常上傳失敗，請把發生失敗當下的**照片大小、Wi-Fi 或行動網路、手機廠牌**告訴我，會更容易鎖定問題。

## 訪客上傳是怎麼運作的

1. 首頁「上傳照片」進去是一個新頁面，會列出**目前所有人已經上傳**的照片（不是只有自己上傳的）。
2. 按右下角「新增照片」選一張或多張圖，上傳成功會馬上出現在畫面最上方（自己看到的是樂觀更新，不用等重新整理）。
3. 別人上傳的新照片，你**不會自動看到**——這是刻意的設計，做法是在手機上「下拉再放開」觸發更新（沒有下拉手勢的裝置，用右上角的重新整理圖示按鈕）。不做成自動即時同步，是因為每次同步都要問一次 Apps Script，訪客一多容易觸發限流；下拉更新讓「什麼時候問伺服器」由使用者自己決定。
4. 訪客**只能新增**，網頁完全沒有刪除或修改別人照片的功能，這點在 `gas.txt` 的伺服器端也有把關（見下面「基本防濫用機制」）。
5. 想清掉不恰當的上傳，或整批把訪客照片併入精選相簿，請直接到雲端硬碟的「訪客上傳」資料夾手動處理——這支程式故意不提供任何刪除功能給網頁，包括給你自己用的都沒有，這是為了確保訪客端的程式碼裡不存在任何「刪除」的程式碼路徑可以被找到、被濫用。管理照片的入口只有一個，就是你自己的 Google 雲端硬碟。

## 基本防濫用機制

你要求的三項防護都做在 `gas.txt`（伺服器端，訪客無法繞過）：

- **單檔 20MB**：超過的檔案，伺服器直接拒絕（`too_big`）。網頁端也會先擋一次（`config.js` 的 `uploadMaxBytes`），選到太大的檔案會直接跳過、不會浪費流量上傳到一半才被拒絕，但**真正把關的一定是伺服器端**，這是因為瀏覽器端的檢查可以被繞過（例如有人不透過這個網頁、直接對 Apps Script 發請求），伺服器端的檢查才是真正擋得住的那一道。
- **只能是圖片格式**：伺服器只認得 `image/jpeg`、`png`、`webp`、`gif`、`heic`、`heif` 這幾種（`gas.txt` 的 `ALLOWED_UPLOAD_TYPES`），其他一律拒絕（`bad_type`）。這是檢查瀏覽器回報的檔案類型，不是真的去拆解檔案內容比對，算是基本防護；如果有人刻意把其他檔案偽裝成圖片類型硬塞進來，這道防護擋不住，但這已經超出「基本防濫用」的範圍，真要做到這麼嚴格通常需要額外的內容掃描服務。
- **上傳頻率限制**：全站每分鐘最多 `MAX_UPLOADS_PER_MINUTE`（預設 20）張，超過會請訪客稍後再試（`rate_limited`）。因為訪客不需要登入、沒有身分可以分別限制，這裡只能做「全站」而不是「每人」的限制，且用的是 Apps Script 的 CacheService 做簡單計數，在極端同時湧入的情況下計數不會完全精準，但用來擋掉單純的洗版流量已經足夠。

**這些都是「基本」防護，不是萬無一失**：沒有身分驗證，代表無法真正防止有心人刻意繞過（例如自己寫程式直接呼叫 Apps Script，而不是透過這個網頁）。如果之後發現有人濫用，最直接的做法是到 Apps Script 把 `MAX_UPLOADS_PER_MINUTE` 調低，或暫時把 `UPLOAD_FOLDER_ID` 的共用權限收回。

## 多張下載：打包或逐張（V1.4）

「相片集」多選照片後按「下載」，會先跳出一個小選單：

- **打包下載（ZIP）**：跟之前一樣，全部裝進一個壓縮檔下載，適合在電腦上解壓縮。
- **逐張下載**：不壓縮，每張照片各自觸發一次下載，適合用手機的人——很多人手機沒有安裝解壓縮 App，收到 `.zip` 檔反而不知道怎麼打開，這個選項下載完直接就是一張張照片，能直接在系統相簿看到。

**逐張下載時，瀏覽器可能會跳出「這個網站要下載多個檔案」的確認視窗**（Chrome 尤其明顯），這是瀏覽器自己的安全機制，不是程式故障——目的是避免網站偷偷觸發一堆下載。每張照片下載之間我加了約 0.35 秒的間隔以降低被瀏覽器擋下的機率，但無法完全避免這個提示，第一次使用時麻煩留意畫面上是否有「允許」的按鈕。單張下載（點開燈箱後的下載按鈕）不受影響，本來就是逐張、沒有這個問題。

## 二、Google 雲端硬碟與 Apps Script 設定

### 1. 建立「兩個」資料夾

V1.3 開始，精選相簿跟訪客上傳是**完全分開**的兩個資料夾：

| 資料夾 | 放什麼 | 誰能新增 |
|---|---|---|
| 精選相簿（例如 `photo`） | 新人自己挑選、要公開的照片 | 只有你自己（直接在雲端硬碟操作） |
| 訪客上傳（例如 `photo-uploads`） | 訪客透過網頁上傳的照片 | 任何開啟網頁的訪客（透過「上傳照片」頁面） |

兩個都建好之後，記下各自的資料夾 ID（網址 `/folders/` 後面那一串）。

首頁的喜帖背景照片已經包在網站檔案裡（`assets/hero.jpg`），**不需要**放進任何一個資料夾。

### 2. 共用設定（兩個資料夾都要做，只做一次）

對**兩個資料夾**分別按右鍵 → **共用** → 一般存取權 → **知道連結的任何人** → **檢視者**（不是編輯者——訪客上傳靠的是 Apps Script 用你的身分寫入，不是訪客自己被授權去改資料夾，所以檢視者權限就夠了，也比較安全）。
資料夾內現有與之後新增的檔案都會沿用這個權限，程式不需要、也不會逐一修改檔案的共用設定。

### 3. Apps Script

1. 到 <https://script.google.com> 建立專案，把 `gas.txt` 的內容貼上，將 `GALLERY_FOLDER_ID` 換成精選相簿的資料夾 ID、`UPLOAD_FOLDER_ID` 換成訪客上傳資料夾的 ID
2. 在編輯器選 `testRun` 函式 → **執行**，依提示授權，並在「執行記錄」確認有印出兩份圖片清單（精選相簿與訪客上傳，此時訪客上傳應該是空的）
3. **部署 → 新增部署作業 → 網頁應用程式**，執行身分選「我」，誰可以存取選「任何人」，複製 `/exec` 網址貼到 `config.js` 的 `imagesSource`
4. 之後如果修改了 `gas.txt`：**部署 → 管理部署作業 → 編輯 → 版本選「新版本」→ 部署**。網址不變，不需改 `config.js`

新增或更換精選相簿的照片後，最多約 5 分鐘會出現在網站上（快取 300 秒，執行 `clearCache` 可立即清除）。訪客上傳的快取只有 20 秒，是刻意設短的，讓「下拉更新」感覺得到差異。

### 4. 版本相容性

V1.3 的網頁只認得新版 `gas.txt` 的訪客上傳功能——如果你還在用 V1.0～V1.2 的 `gas.txt`（沒有 `doPost`、沒有 `UPLOAD_FOLDER_ID`），精選相簿的瀏覽、下載都完全正常，但「上傳照片」頁面會顯示載入失敗（因為 `?action=uploads` 這個端點不存在），上傳按鈕點下去也不會成功。想要訪客上傳功能，**這次必須重新部署 `gas.txt`**，並記得補上 `UPLOAD_FOLDER_ID` 跟它的共用設定，這點跟以前幾版「不換也沒關係」不一樣。

## 三、隱私與安全評估

### 結論

以目前程式的寫法，**雲端硬碟裡其他沒有共用的檔案不會因此外洩**：
- `doGet()` 不接受任何參數，資料夾 ID 固定寫在程式裡，訪客無法指定其他資料夾或檔案
- 只回傳「該資料夾內、格式為圖片」的檔案 ID 與檔名
- 沒有回傳任何其他 Drive 資料，也沒有把其他檔案設為公開

但整個系統的性質是「**知道連結的任何人都能看**」，下列幾點需要留意。

### 需要留意的風險

1. **相簿等同公開**：`/exec` 網址寫在 `config.js`，而 `config.js` 放在 GitHub 上。任何人只要看到這個網址，就能取得全部照片的清單與連結。這與「有網址者才能開啟」的預期相同，但不是真正的存取控制。
2. **放進資料夾的圖片都會公開**：只要圖片放進這個資料夾，就會出現在相簿。請不要把私人照片放進去。
3. **權限不會隨移動而收回**：舊版程式對每張圖片單獨設定「知道連結的任何人」。這種設定是**跟著檔案**的，即使之後把檔案移出資料夾、程式停止列出，連結仍然有效。V1.1 預設改為只在資料夾層級共用（`AUTO_SHARE_FILES = false`），之後只要把檔案移出資料夾就不再公開。**舊版已經逐一設定過的檔案，需要手動處理**：不想公開的，請在檔案上重新設為「限制」。
4. **程式擁有完整雲端硬碟權限**：Apps Script 以「我」的身分執行，授權時 Google 會顯示它能存取你的所有雲端硬碟檔案。Apps Script 的 `DriveApp` 沒有更窄的權限可選。目前的程式碼不會外洩，但這也代表**日後若程式被改壞、或帳號被入侵，影響範圍是整個雲端硬碟**。
5. **原始檔可能含有位置資訊**：下載使用原始檔（`=s0`），原始照片可能包含拍攝地點（GPS）等 EXIF 資料。若有隱私考量，請先移除再上傳，或把 `config.js` 的 `downloadPx` 設為 `2048` 使用縮小後的版本。
6. **錯誤訊息**：舊版在出錯時會把原始錯誤內容回傳給訪客。V1.1 改為只回傳 `server_error`，詳細內容只留在 Apps Script 執行記錄。

### V1.3：訪客上傳額外帶來的風險

開放訪客上傳，跟單純唯讀瀏覽是不一樣等級的風險，請務必看過這幾點：

1. **上傳後立刻公開，沒有人審核**：訪客按下上傳，照片馬上所有人都看得到，中間沒有任何「新人先確認過才公開」的審核關卡。這代表理論上任何開啟連結的人，都可以上傳不相關、不恰當、甚至冒犯性的圖片，而且會在你發現並手動刪除之前，一直被所有訪客看到。
2. **伺服器只檢查「宣稱的」檔案類型，不檢查內容**：`gas.txt` 會擋掉「不是圖片格式」的檔案，但沒有辦法自動判斷一張圖片「內容是否恰當」——這已經超出「基本防濫用」的範圍，需要額外的內容審核服務才做得到，這版沒有做。
3. **無法追查是誰上傳的**：整個系統沒有登入機制，Apps Script 收到的上傳請求也沒有記錄是誰送出的。如果有不恰當的內容，你能做的只有「刪除那個檔案」，沒辦法封鎖或追究上傳者。
4. **速率限制擋得住洗版，擋不住持續上傳**：`MAX_UPLOADS_PER_MINUTE` 能擋掉短時間內大量灌入的流量，但如果有人有耐心地持續慢慢上傳，還是可能長期消耗你的雲端硬碟空間，速率限制只是拉高門檻，不是完全阻絕。
5. **訪客照片一樣可能含有 GPS 等定位資訊**：跟精選相簿的原始檔一樣，手機拍的照片常帶有拍攝地點的 EXIF 資料，訪客上傳的原始檔也是直接存進 Drive，沒有經過去除metadata 的處理。

**這代表什麼**：這個功能適合辦活動期間、對象是受邀賓客的場景（例如婚禮當天用 QR Code 讓賓客現場分享照片），但因為連結一旦外流就等於對外公開，請不要把它當成完全不需要照看的自動化系統。

**建議的做法**：
- 婚禮前後這段期間，請養成**每天檢查一次訪客上傳資料夾**的習慣，尤其是活動剛結束、上傳最集中的那幾天。
- 覺得上傳的人數或頻率不太對勁，可以到 Apps Script 把 `MAX_UPLOADS_PER_MINUTE` 調低，或直接把 `UPLOAD_FOLDER_ID` 這個資料夾的共用權限暫時收回（改回「限制」），upload 端點就會失敗，等你想重新開放時再改回「知道連結的任何人」即可，不需要重新部署程式。
- 如果之後想要「訪客上傳的照片，要等你按下核准才會公開」這種審核機制，這是可以做的（例如：訪客上傳先進一個沒公開的暫存資料夾，你確認過後再搬到公開的訪客上傳資料夾），但這一版沒有做，跟我說一聲我可以再加上去。

### 一般建議（精選相簿與訪客上傳都適用）

- **最有效的做法**：用一個**專門放相簿的 Google 帳號**來建立 Apps Script 與資料夾（不要用放個人文件的主帳號）。這樣即使發生前面第 4 點（程式擁有完整雲端硬碟權限）的狀況，也不會碰到你的個人檔案。
- 兩個資料夾都只放你確定要公開的內容。
- 「雲端硬碟資料夾」與「Google 相簿（Google Photos）」是不同的服務，這套程式只讀雲端硬碟，不會碰到 Google 相簿裡的內容。
- 如果照片真的需要保密，請不要使用「知道連結的任何人」，需要改用要求登入的架構。

## 四、首頁的美術素材是怎麼做的

你給的參考圖裡，新人姓名、花押字、「Our Wedding Day」都是**燒錄在照片裡的文字**，沒辦法跟著切換語言。我把這幾樣分開處理：

- `assets/hero.jpg`：把你上傳的照片裡的文字、花押字用修圖方式移除，只留下乾淨的照片，放大成 2 倍解析度。這張照片是直接沿用你上傳的圖，不是另外生成的。
- `assets/monogram.png`：從原圖裁下「CK」交織花押字與兩側的月桂葉，去背存成透明 PNG，繼續當裝飾圖案用（花押字本身是圖案，中英文都一樣，不需要跟著翻譯）。
- `assets/leaf-tl.png` / `leaf-bl.png` / `leaf-br.png` / `sprig.png`：原圖卡紙區的葉片裝飾，去背後重複使用在新版面的四個角落。
- 「Yuan Kuan & Cristine」「YK & C」「Our Wedding Day / 我們的婚禮」現在是**即時渲染的文字**，不是圖片，所以才能真的跟著中英文切換；新人姓名是專有名詞，中英文都顯示同樣的英文拼法。

**背景不會變形也不會裁到主體**：照片區的寬高比直接設成跟這張照片完全一樣（622:723），不管螢幕多寬多高，照片永遠完整顯示、等比例縮放，不會裁掉月桂葉或新人姓名，也不會被拉伸。桌面瀏覽器螢幕通常很寬但不會那麼高，直接整頁滿版會讓照片被拉得極高不好看，所以電腦版會把整個首頁縮成一張置中的卡片（寬度上限 460px，帶圓角與陰影），手機版則維持滿版。想換成別的照片，直接替換 `assets/hero.jpg`（維持接近 622:723 的直式比例效果最好）即可，不需要改程式碼。

首頁的中文字型使用「Noto Serif TC」、英文使用「Cormorant Garamond」，從 Google Fonts 載入（`index.html` 的 `<head>` 裡）。這是本專案目前唯一會連到 Google 以外網域的地方；如果你的訪客所在地區連不到 `fonts.googleapis.com`，字型會自動退回系統內建的襯線字體，不影響使用。

## 五、載入大量圖片的效能

### 原因

進入「圖片預覽」時，主要的延遲來自：

1. **Apps Script 回應慢**：冷啟動與逐檔讀取 Drive 資料。舊版還有兩個問題：每 6 小時會對每張圖片重新呼叫一次 `setSharing`（照片多時可能要好幾十秒甚至逾時）；清單快取超過 100 KB（約 400 張以上）時 `cache.put` 會丟出例外，導致整個回應變成錯誤。
2. **一次建立所有縮圖的 DOM，並讓瀏覽器預載很遠**：600 張就是 600 個項目、3000 多個節點，首屏就發出約 40 個圖片請求。
3. **縮圖偏大**：`=w600` 的縮圖顯示在約 190 px 的格子裡。
4. **進入頁面後才開始向 Google 要清單**。

### V1.1 的作法

| 項目 | 作法 |
|---|---|
| 提早取得清單 | 一開啟網頁就在背景向 Apps Script 取清單與背景圖，通常在使用者選完語言前就已備妥 |
| 本機快取 | 清單存在瀏覽器裡，第二次以後進入相簿**立即顯示**，再於背景更新；Apps Script 暫時失敗時仍可瀏覽 |
| 分批渲染 | 一次只建立 60 張，往下捲動接近底部才建立下一批（`chunkSize`）；選取、全選、下載都以完整清單為準 |
| 受控延遲載入 | 只下載「可視範圍 + 上下約 600 px」內的縮圖，首屏 8 張優先載入 |
| 縮圖最佳化 | 依欄數與螢幕密度自動要求 `=s{尺寸}-c`（伺服器端裁成方形），手機約 400 px |
| 骨架畫面 | 沒有快取時先顯示灰色佔位格，而不是轉圈圈 |
| 燈箱 | 先顯示已載入的縮圖，再換成符合螢幕大小的圖，並預載前後各一張 |
| Apps Script | 只回傳 ID 與檔名（體積小、快取不會超過 100 KB）、移除逐檔 `setSharing`、快取 300 秒 |
| 更新時機 | 清單有變動時，若正在選取或看燈箱，等結束後才套用，不會打斷操作 |

### 實測（模擬環境）

條件：600 張照片、Apps Script 延遲 1.5 秒、每張圖片延遲 0.12 秒、使用者在選單停留 2 秒後點「圖片預覽」、手機螢幕。

| | 舊版 | V1.1 |
|---|---|---|
| 點擊後第一張縮圖出現 | 2.7 秒 | 0.3 秒（第二次以後同樣 0.3 秒） |
| 首屏圖片請求數 | 40 | 16 |
| 首屏縮圖流量 | 約 2.1 MB | 約 0.57 MB |
| 頁面節點數 | 3134 | 442 |

這是用模擬的伺服器量測，用來比較「網頁端」的改善。實際的 Apps Script 冷啟動時間與 Google 圖片伺服器的速度，會隨當下狀況變動。

### 可調整的參數（`config.js`）

- `chunkSize`：每批渲染的張數，預設 60
- `downloadPx`：下載尺寸，`0` 為原始檔；照片很多又要打包下載時，建議設 `2048`，可大幅降低 zip 體積與手機記憶體壓力

## 六、需要在實機確認的事

1. **打包下載需要 Google 圖片伺服器允許跨網站讀取（CORS）**。我沒辦法在沒有外網的環境驗證這點。請上線後選兩三張照片按「打包下載」試一次。如果出現「下載失敗…CORS」，再回報，需要改用其他下載方式。預覽與單張下載（會改為在新分頁開啟）不受影響。
2. Google 對同一來源大量請求偶爾會限流（HTTP 429）。已大幅減少請求數；如果照片達到上千張仍有縮圖載入失敗，可調小 `chunkSize`。
3. 打包下載會把所有照片放在手機記憶體中壓縮，一次選很多張的原始檔可能導致頁面重新整理。建議搭配 `downloadPx: 2048`。
4. **Google Fonts 是否能正常載入**。我用瀏覽器模擬測試過版面（中英文、手機、電腦、離線都沒問題），但沒辦法在沒有外網的環境實際確認 `fonts.googleapis.com` 的字型顯示效果，理論上會自動套用、載入不了時會自動退回系統字體，上線後麻煩留意一下標題字型是否如預期。
5. 首頁安裝到手機主畫面後的圖示（喜帖花押字），建議實際安裝一次確認顯示效果，不同手機的圖示裁切方式略有差異。
6. **訪客上傳這個功能，務必實機測試過一輪再正式分享連結**：用手機的行動網路（不是 Wi-Fi，比較貼近婚禮現場的實際狀況）試上傳一張正常拍的照片，確認它出現在畫面上；換一台裝置開啟「訪客照片」頁面，確認能看到剛剛那張；下拉更新看看有沒有反應；也故意選一個 20MB 以上的檔案、或選一個 .txt 檔試試看，確認會被擋下並顯示對應的原因，而不是卡住不動或顯示籠統的錯誤。
7. **上傳走的技術路徑（text/plain 繞過 CORS 預檢）我沒辦法在沒有真實 Apps Script 的環境測到**。這是 Apps Script 網頁應用程式的已知限制與業界慣用解法（見開頭的技術說明），理論上會動，如果上線後「上傳照片」還是一直卡住或報錯，請把當下的錯誤訊息（現在應該會顯示更明確的原因，例如「太大」「格式不符」「逾時」，而不是都顯示同一句話）告訴我，會更容易排查。
8. **V1.4 加了上傳前自動縮圖，實機測試時留意一下畫質是否符合預期**。預設長邊壓到 2400px、JPEG 品質 0.85，一般用來在網頁上瀏覽、分享綽綽有餘，但如果新人希望保留手機拍攝的完整畫質（例如想事後拿去印相本），可以把 `config.js` 的 `uploadMaxDimension` 調大或設成 `0`（關閉縮圖），但要知道這樣做會讓上傳變慢、失敗機率也會回升，尤其是在婚禮現場人多網路壅塞的時候。
9. **逐張下載時瀏覽器可能跳出「允許多次下載」的提示**（見上方「多張下載：打包或逐張」），實機測試時留意一下這個提示會不會擋住整個下載流程、要不要手動按允許。

## 七、部署到 GitHub Pages 與 QR Code

1. 把這個資料夾裡的所有檔案上傳到 GitHub repository（覆蓋舊檔案）
2. Settings → Pages → Deploy from a branch → `main` / root
3. 網址為 `https://你的帳號.github.io/repository名稱/`
4. 開啟 `你的網址/qr.html` 產生 QR Code 並下載

想隱藏手機的網址列：把網站「加入主畫面」，之後從主畫面圖示開啟（選單頁面會提示）。網頁程式無法在一般瀏覽器分頁中強制隱藏網址列。

## 八、本機測試

```bash
python3 -m http.server 8000
```

開啟 <http://localhost:8000>。不使用 Google 時，把 `config.js` 的 `imagesSource` 改成 `"images.json"`——這種本機模式下「相片集」可以正常瀏覽，但「訪客照片」頁面會顯示載入失敗，因為上傳與訪客照片清單都需要真的連到 Apps Script，本機的 `images.json` 只是一份靜態清單，沒有對應的伺服器可以接收上傳。

## 九、常見修改

- 修改文字或新增語言：`index.html` 裡搜尋 `const I18N`
- 換掉首頁背景照片：替換 `assets/hero.jpg`（直式照片、寬高比接近 622:723 效果最好），花押字與葉片裝飾在 `assets/monogram.png`、`assets/leaf-*.png`、`assets/sprig.png`
- 調整首頁配色：`index.html` 最上方 `:root` 的 `--btn`（按鈕底色）、`--cream`（卡紙底色）、`--accent`（強調色）
- 調整長按時間：`config.js` 的 `longPressMs`
- 調整訪客上傳的單檔大小上限：**同時**改 `config.js` 的 `uploadMaxBytes` 與 `gas.txt` 的 `MAX_UPLOAD_BYTES`，兩邊要填一樣的位元組數，只改一邊會造成網頁端跟伺服器端擋下的標準不一致
- 調整每分鐘上傳張數上限：`gas.txt` 的 `MAX_UPLOADS_PER_MINUTE`
- 想再開放更多圖片格式（例如 avif）：`gas.txt` 的 `ALLOWED_UPLOAD_TYPES` 陣列加上對應的 MIME type
- 暫停訪客上傳（不想關掉整個網站，只想先停止接受新照片）：到雲端硬碟把 `UPLOAD_FOLDER_ID` 那個資料夾的一般存取權改回「限制」，不需要重新部署程式；想重新開放再改回「知道連結的任何人」即可
- 調整上傳前縮圖的長邊上限或畫質：`config.js` 的 `uploadMaxDimension`（px，設 `0` 關閉縮圖）、`uploadJpegQuality`（0～1）
- 調整上傳逾時時間：`config.js` 的 `uploadTimeoutMs`（毫秒），訪客反應「網路明明在動、卻一直顯示逾時」可以調高
- 調整下載選單的文字：`index.html` 裡搜尋 `downloadAsZip` / `downloadIndividually`（含各自的一行說明文字 `...Hint`）
